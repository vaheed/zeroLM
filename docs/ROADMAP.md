# ZeroLM: Research and Engineering Roadmap

**Document status:** Proposed research plan  
**Date:** 2026-11-06  
**Repository baseline:** `vaheed/zeroLM`, default branch `main`  
**Primary objective:** Build a CPU-first neural language system with no offline pretraining, whose parameters and persistent memory can develop from its own chronological stream of input, prediction, feedback, and interaction.

---

## 0. Executive decision

ZeroLM should not be designed as a small Transformer with its KV cache and context window removed. It should be developed as a **recurrent, online-learning neural language system with fast associative weights, persistent weight-resident memory, and a controlled weight-space programming layer**.

The target architecture is a hybrid:

1. **A byte-level language interface** so every UTF-8 input is representable from the first run without a pretrained tokenizer or vocabulary.
2. **A recurrent neural sequence engine** that carries a bounded working state from token to token. A gated state-space / linear-recurrent core is the primary candidate; a small GRU-like recurrent core and a local-attention hybrid are comparison baselines.
3. **A next-token prediction head** that can learn from the actual chronological input stream. The target token is the next observed token, not a label generated by the model itself.
4. **Fast plastic weights** updated online with explicit, bounded local rules such as normalized delta-rule / fast-weight associative updates.
5. **Persistent associative memory tensors** stored inside the model checkpoint and read through neural key-query operations. This is not an unlimited memory: it has finite capacity, interference, and retrieval limits that must be measured.
6. **A slow weight-space programming system** that can propose structural or skill-level weight edits, validate them, run regression tests, and atomically accept or reject them.
7. **A language decoder** that generates novel token sequences from the recurrent state rather than selecting canned response strings.
8. **An evaluation and governance layer** that measures acquisition, generalization, retention, forgetting, calibration, resource use, and the provenance of every weight change.

### 0.1 The terminology must change

The current repository describes itself as a “Zero-Training Language Model” and prohibits all training. That definition conflicts with the new goal of improving from experience. The technically coherent contract is:

> **Zero Offline Pretraining. Lifelong Online Learning. No Imported Model Weights.**

The initial model is not pretrained on a corpus. During its lifetime it is allowed to update selected weights from streaming observations and feedback. Those runtime updates are learning. They must not be described as “no learning” or “no training of any kind.”

The default research track should first test local, non-backpropagated plasticity and direct weight-space edits. A small online-gradient implementation may be kept as a clearly labelled research control, not silently introduced into the mainline. If all gradient-based updates are forbidden forever, that restriction must be accepted as a major capability limit; it cannot be hidden behind the term Weight-Space Programming.

### 0.2 What this roadmap does not promise

This plan does **not** guarantee a seven-year-old level of cognition, much less a twenty-year-old level. No known research result establishes that an initially untrained neural network can acquire broad human language and world knowledge through a small CPU-only online stream. The roadmap is designed to test that hypothesis in falsifiable steps. A successful parser, memory demo, or low perplexity on a tiny synthetic language is not evidence of human-level understanding.

**Decision:** preserve v0.2 and Next as historical baselines. Do not try to stretch the current grammar parser into a general LM by adding hundreds of words and canned responses. Build the new engine as a separate research track, then compare it against the existing baselines.

## 2. Research findings and architectural implications

This section summarizes relevant work checked for this roadmap. These works provide design evidence, not proof that ZeroLM's stronger objective has already been solved.

### 2.1 Recurrent and state-space language models

- **Mamba-2 / State Space Duality:** the ICML 2024 paper connects structured state-space models and attention, and presents a selective SSM design with linear-time recurrent inference. It supports testing recurrent state-space blocks as a serious sequence-modeling family rather than assuming that a Transformer is mandatory. Its demonstrated language models are trained; it does not prove that hand-programmed weights will understand language without learning. [PMLR paper](https://proceedings.mlr.press/v235/dao24a.html).
- **RWKV-7:** the 2025 paper describes a recurrent sequence architecture with constant memory and constant per-token inference cost, plus a generalized delta-rule update. Its demonstrated language models were trained on a very large corpus. The useful lesson is the recurrent state and gated update design, not a claim that RWKV learns a language from nothing. [arXiv paper](https://arxiv.org/abs/2503.14456).
- **xLSTM 7B:** demonstrates that recurrent architectures can be used for competitive language-model inference at scale, but its models are trained. It is a comparison point for recurrent design and CPU/runtime profiling, not a blueprint for zero-pretraining acquisition. [arXiv paper](https://arxiv.org/abs/2503.13427).

**Implication for ZeroLM:** use a recurrent state as the default sequence interface. Test at least two genuinely different recurrent cells, and do not assume that one particular SSM formulation is automatically best for a tiny CPU-first model. A fixed-size state removes the need to retain all past Key/Value tensors, but it does not create unlimited memory: relevant information can be compressed, overwritten, or forgotten.

### 2.2 Test-time neural memory and fast weights

- **Titans: Learning to Memorize at Test Time** introduces a neural long-term memory module that learns to store historical information and is combined with attention for current context. The paper explicitly distinguishes a recurrent fixed-size state from an attention context and uses a learned neural memory for longer-term information. Its language-model experiments use trained models; it is not evidence that the memory module can bootstrap language by itself. [NeurIPS 2025 paper](https://papers.neurips.cc/paper_files/paper/2025/hash/a4ca07aa108036f80cbb5b82285fd4b1-Abstract-Conference.html) · [arXiv](https://arxiv.org/abs/2501.00663).
- **Fast-weight memory** has a long history. Schmidhuber's 1992 work describes rapidly changing weights used as temporal/associative memory, but the controller in that work is gradient-trained. [MIT Press](https://doi.org/10.1162/NECO.1992.4.1.131).
- **Differentiable plasticity** demonstrates recurrent networks with Hebbian plastic connections, but the plasticity itself is optimized with backpropagation. It supports the idea of separating stable connection weights from plastic state, while also showing that learning the plasticity rule is a separate problem. [PMLR 2018](https://proceedings.mlr.press/v80/miconi18a.html).

**Implication for ZeroLM:** prototype a fast associative memory as a weight tensor with an explicit update rule. Keep fast memory, persistent semantic memory, and slow cognitive-core weights as separate tensor groups. Do not label a separate JSON database as “weight memory.” Persist the memory tensors in the same model checkpoint and retrieve them through the neural engine.

### 2.3 Weight-Space Programming (WSP)

A November 2, 2026 MIT CSAIL blog post, *Sparks of Weight-Space Programming*, reports early experiments in which GPT-6 Astra reads, writes, and edits neural network weights. It reports hand-authored small game policies from zero weights, weight edits to a trained control policy, and edits to a pretrained Qwen model. The post itself also reports a negative result: editing Gemma did not create math capability that appeared to be absent. In the Qwen experiment, the base model was already pretrained; the reported improvement was a targeted edit, not language acquisition from zero. The authors describe this as early work and say they are building a benchmark and harness. [Original post](https://rikiyat.github.io/blog/weight-space-programming/).

**Implication for ZeroLM:** WSP is a way to design, inspect, and patch a network's parameters. It is not, by itself, a learning algorithm or an explanation of how an untrained network acquires natural language. Initially, WSP patches will be authored by humans or an external development-time programmer and checked by the repository's deterministic harness. ZeroLM must not depend on a pretrained external LLM at runtime. An internal neural patch proposer is a later research milestone and must prove that it can generate useful, safe patches without an external model.

### 2.4 Language acquisition and child-development benchmarks

- The **BabyLM 2026 findings** report that GPT-BERT remained a strong foundation for sample-efficient pretraining and that more training epochs, recursion/looping, and data preprocessing were associated with stronger results. These are results from pretraining under restricted data budgets, not from zero-pretraining systems. [ACL Anthology 2026](https://aclanthology.org/2026.babylm-main.37/).
- **CHILDES / childes-db** provides versioned child-language data. The 2026.1 release reports 24.2 million utterances and 89 million tokens. It can support controlled exposure-stream experiments and evaluation research, subject to corpus-specific terms and citations. It must not be embedded into initial weights if the zero-offline-pretraining rule is to remain meaningful. [childes-db](https://langcog.github.io/childes-db-website/).

**Implication for ZeroLM:** text-only input is enough to test syntax and parts of language modelling, but not enough to claim that the system has developed the full grounded experience of a child. A later phase must add interactive environments and, optionally, visual/audio input. Age labels should be replaced by capability profiles and independently normed assessments.

### 2.5 Continual-learning evaluation

Continual-learning research distinguishes the ability to learn new information from the ability to retain old information and transfer knowledge to new tasks. ZeroLM must report learning curves, average performance, forgetting, backward transfer, forward transfer, calibration, resource use, and per-task results—not just the final score. [Continual LLM survey](https://doi.org/10.1145/3716629) · [systematic review](https://doi.org/10.1016/j.neunet.2025.108226).

## 3. Target architecture

### 3.1 High-level data flow

```text
UTF-8 input stream / feedback / optional environment observations
                         |
                         v
              Byte-level tokenizer
                         |
                         v
            Programmed input embedding
                         |
                         v
           Recurrent Neural Language Core
             |             |             |
             |             |             +--> Next-token distribution
             |             |
             |             +--> Working recurrent state (session-local)
             |
             +--> Query/key/value projections
                         |
              +----------+----------+
              |                     |
              v                     v
      Fast plastic weights     Persistent memory tensors
      (online updates)         (checkpoint-resident)
              |                     |
              +----------+----------+
                         |
                         v
             Semantic / episodic retrieval
                         |
                         v
              Language decoder / output
                         |
                 observed feedback
                         |
                         v
             Online Learning Controller
                         |
          +--------------+---------------+
          |                              |
          v                              v
  Local plasticity updates        WSP patch proposal
                                         |
                                         v
                              validator + regression gate
                                         |
                              accept / reject / rollback
```

### 3.2 Core modules and their responsibilities

| Module | Responsibility | State / parameters | Must not do |
|---|---|---|---|
| `Tokenizer` | Convert UTF-8 text to deterministic byte IDs; preserve offsets | Fixed byte alphabet and control IDs | Load a pretrained vocabulary |
| `InputEncoder` | Map byte/subword sequences to numeric vectors | Programmed initial embedding; later plastic embedding tensors | Claim semantic understanding merely from IDs |
| `RecurrentCore` | Process sequence and update hidden state | Slow neural weights + session-local recurrent state | Require an ever-growing KV cache |
| `PredictionHead` | Predict next byte/token | Output weights, online-updated | Emit only canned response paths |
| `PlasticityEngine` | Apply bounded input/target/error-dependent updates | Fast weights, eligibility traces, update-rule constants | Update on the model's own unverified claim as if it were truth |
| `AssociativeMemory` | Store/retrieve key-value and relation patterns | Persistent memory tensors in model checkpoint | Use an external vector DB as source of truth |
| `ConceptLayer` | Represent entities, attributes, relations, events, and uncertainty | Concept/relation tensors | Encode a complete English ontology by hand |
| `Reasoner` | Compose stored relations and learned patterns | Recurrent activations + explicit inference operators | Treat every plausible inference as a verified fact |
| `LanguageDecoder` | Generate token sequences from state and retrieved memory | Decoder weights | Use fixed complete-sentence templates as the primary generator |
| `WSPController` | Diagnose traces and propose bounded structural edits | Architecture manifest + patch DSL | Write arbitrary unchecked bytes into active weights |
| `Consolidator` | Select what should persist and protect prior abilities | Stability scores, protected test suite, memory metadata | Assume repeated exposure proves truth |
| `CheckpointStore` | Atomically persist current model tensors and version metadata | One versioned model checkpoint | Store the semantic source of truth in sidecar transcripts |
| `Evaluator` | Measure learning, transfer, forgetting, and efficiency | Frozen and generated test sets | Feed hidden test labels back into learning |

### 3.3 Weight groups

The serialized model checkpoint should declare at least these groups:

```text
W_CORE       recurrent encoder/core/decoder parameters
W_EMBED      byte or subword embedding parameters
W_FAST       rapidly updated associative weights
W_MEMORY     persistent semantic and episodic memory tensors
W_SKILL      optional skill/circuit modules created through WSP
W_META       bounded update-rule parameters and architecture metadata
```

`W_CORE` and `W_SKILL` are slow parameters. They may evolve only through the patch/consolidation protocol. `W_FAST` and `W_MEMORY` may be written online using explicit update rules. `W_EMBED` may be updated only after its update rule passes stability and retention tests. Session state is not part of persistent memory and must be resettable.

### 3.4 Recurrent core candidate

Do not hard-code a claim that “Mamba is the answer.” Run a small, parameter-matched architecture bake-off:

1. **Gated recurrent baseline:** a compact GRU-like cell with multi-timescale state.
2. **Linear state-space / gated recurrence:** a stable diagonal or block-diagonal state update with input-dependent gates, inspired by SSM/RWKV design principles.
3. **Fast-weight recurrent cell:** recurrent state plus an online associative matrix updated by a normalized delta rule.
4. **Hybrid control:** recurrent core plus a small fixed local-attention window; this is a comparison arm, not the default target.

Select the winner based on chronological learning, held-out generalization, forgetting, CPU latency, RAM, and traceability. A recurrent core can avoid storing all prior keys and values, but it still has a finite state and can lose information. A short local window may be retained as a bounded aid if experiments justify it.

### 3.5 Online memory update candidate

Start with a mathematically explicit fast-weight update. For key vector `k`, target/value vector `v`, and memory matrix `M`:

```text
v_hat = M * k
error = v - v_hat
M_next = decay * M + learning_rate * error * k^T / (epsilon + dot(k, k))
```

This is a candidate normalized delta-rule update, not a proven general-purpose memory solution. Test collisions, capacity, overwriting, interference, exact recall, paraphrase retrieval, and forgetting. Keep dimensions modest and use low-rank or block-sparse storage if CPU measurements require it.

### 3.6 Bootstrap constraints

A model with no pretrained weights does not begin with English understanding. The initial system needs a small **programmed bootstrap**:

- byte-level input encoding;
- basic numerical and sequence operations;
- a tiny explicit teaching/control protocol (`teach`, `ask`, `correct`, `confirm`, `forget`, `repeat` or equivalent);
- a typed internal representation for token spans, entities, relations, prediction targets, and update proposals;
- a trace format and a deterministic update controller.

This is engineered prior structure, not learned language knowledge. The bootstrap must be documented and counted. Natural-language competence beyond this seed must be acquired from subsequent chronological experience.

## 4. Research rules and non-negotiable invariants

1. No pretrained model weights, embeddings, tokenizer merges, or hidden model checkpoints.
2. No offline corpus pretraining or offline fine-tuning in the release path.
3. Online learning is allowed and must be reported honestly. Every update must identify its input stream, target/feedback signal, rule, changed tensors, and checkpoint hash.
4. The mainline must first test local plasticity and explicit WSP patches. Backpropagation is not silently introduced. If an online-gradient control is run, it is isolated, labelled, and excluded from the strict mainline unless the project constitution is deliberately revised.
5. Benchmarks must be separated into exposure streams, development tests, and hidden evaluation sets. Hidden labels must never be used by the update controller.
6. Never train on the final evaluation set. A benchmark stream used for online exposure is training input, even if processed one sample at a time; record it as such.
7. The model's own generated answer is not a reliable teacher. Updates need an observed continuation, user correction, deterministic environment outcome, or independently validated signal.
8. Every accepted weight patch is versioned, attributable, reversible, and re-evaluated against frozen regression suites.
9. No self-modification may execute arbitrary code, change the runtime binary, alter CI tests, or edit protected evaluation data.
10. “Seven-year-old” and “twenty-year-old” are aspiration labels only. Report concrete capabilities and benchmark performance instead.

## 5. Phased roadmap and exit gates

Each phase adds an executable test suite. A phase is complete only when its tests run in GitHub Actions, its evidence is uploaded, and its job summary is generated even on failure.

### Phase 2 — Neural compute engine and architecture bake-off

**Goal:** Create a reusable neural runtime rather than another specialized parser.

**Work**
- Add a new Rust workspace or isolated module tree; do not break current `rust/src/next`.
- Implement tensor storage, matrix-vector/matrix-matrix operations, activation functions, normalization, deterministic initialization, and trace capture.
- Implement the four recurrent candidates in Section 3.4 with equivalent parameter budgets.
- Implement state serialization and exact resume of recurrent state.
- Add numeric bounds, finite-value checks, overflow checks, and deterministic seeds.
- Keep the first CPU implementation simple and inspectable. Add SIMD/BLAS only after profiling proves it useful.

**Suggested layout**

```text
crates/
  zerolm-tensor/       # tensors, matrix kernels, deterministic initializers
  zerolm-nn/           # modules, recurrent cells, activations, trace hooks
  zerolm-tokenizer/    # byte IDs and offsets
  zerolm-engine/       # model forward pass and decoder
  zerolm-learning/     # local update rules and eligibility traces
  zerolm-memory/       # associative and persistent weight memory
  zerolm-wsp/          # patch schema, validation, sandbox, rollback
  zerolm-runtime/      # sessions, checkpointing, CLI and API
  zerolm-eval/         # benchmarks and continual-learning metrics
```

**GitHub Actions tests**
- Compare Rust kernels against a small independent Python reference on seeded inputs.
- Numerical parity: `max_abs_error <= 1e-6` for FP32 reference tests, with explicit tolerances for any lower-precision kernel.
- Determinism test: same seed and spec produce byte-identical initialized weights.
- Recurrent equivalence: token-by-token and chunked recurrence produce matching final states where mathematically expected.
- Ablations: zeroing/shuffling key recurrent paths must damage the tasks that depend on them.
- CPU benchmark: report p50/p95 token latency, tokens/sec, peak RSS, parameter count, and checkpoint size.

**Exit gate**
- One recurrent candidate is selected by measured trade-offs, not preference.
- The architecture can process long streams with fixed-size session state and no growing KV cache.
- A clean CPU-only build succeeds on Linux and macOS.

### Phase 3 — Bootstrap language interface and deterministic initialization

**Goal:** Make the system able to receive arbitrary text before it has learned a vocabulary.

**Work**
- Implement UTF-8 byte tokenization (256 byte values plus explicit control tokens); do not require a pretrained BPE/SentencePiece vocabulary.
- Preserve byte offsets so outputs, traces, and corrections can refer to source spans.
- Initialize embeddings and recurrent parameters using deterministic, documented programmatic construction. Do not fetch an embedding table.
- Implement a minimal explicit teaching/control protocol for bootstrapping: present an example, confirm/correct it, ask for recall, and request forgetting.
- Record the complete seed vocabulary and rules. Keep the seed intentionally small.
- Add an optional online subword table only as an experiment after byte-level correctness is stable.

**Deliverables**
- `crates/zerolm-tokenizer/`
- `crates/zerolm-engine/src/bootstrap.rs`
- `model/bootstrap/seed.json`
- `docs/BOOTSTRAP.md`

**GitHub Actions tests**
- Round-trip UTF-8 tests for ASCII, Unicode, punctuation, emoji, and malformed input handling.
- No-OOV test: every valid UTF-8 string is representable.
- Deterministic initialization hash test.
- Static artifact scan proving no pretrained tokenizer or embedding asset is loaded.
- CLI test: a clean model starts, accepts the teaching protocol, emits an inspectable trace, and exits without corrupting weights.

**Exit gate**
- The model can accept arbitrary byte sequences from the first run.
- It is explicitly not claimed to understand arbitrary English at bootstrap.

### Phase 4 — First true online neural language model

**Goal:** Demonstrate online language acquisition rather than phrase lookup or fixed answers.

**Work**
- Implement an autoregressive byte-level next-token prediction head.
- For each observed stream: predict the next byte from prior bytes, then reveal the actual next byte, calculate prediction error, and apply the configured online update.
- Implement and compare:
  1. frozen recurrent baseline;
  2. fast-weight / normalized delta-rule update;
  3. local Hebbian/eligibility-trace variant;
  4. optional research-only online truncated-BPTT control, clearly marked as gradient-based online learning.
- Do not feed an entire corpus through an offline training loop. The experiment runner must expose the stream chronologically, one event at a time, and record each update.
- Use generated compositional text streams first. Add pinned, licensed child-directed-language streams later as optional exposure experiments; never initialize weights from them.
- Report bits-per-byte (BPB), next-byte accuracy, calibration, and learning curves. Include a simple byte n-gram baseline.

**Deliverables**
- `crates/zerolm-learning/src/online_predictor.rs`
- `research/streams/`
- `research/benchmark/language_modeling.py`
- `reports/online-learning/`

**GitHub Actions tests**
- Start from deterministic initial weights and verify initial and final hashes differ after a real update.
- Verify update event log corresponds exactly to observed tokens and prediction targets.
- Verify no future token leaks into the prediction state.
- Verify no update occurs when learning mode is disabled.
- Evaluate held-out continuation and novel combinations never included in the exposure stream.
- Run at least three seeds and report mean, standard deviation, and per-seed curves.
- Require statistically/reproducibly better held-out BPB than the frozen initialized model and the byte-frequency baseline before claiming acquisition. Set the numeric improvement floor after Phase 2 pilot baselines and freeze it before the main experiment.
- Report the online-BPTT control separately; it must never be presented as the strict local-plasticity result.

**Exit gate**
- The same initially untrained architecture improves on unseen continuations after chronological exposure.
- Improvement is not explained only by memorizing seen strings.
- The update rule and its limitations are explicit. If non-gradient plasticity cannot pass, do not hide the failure: either revise the rule or explicitly decide whether online gradient updates are allowed.

### Phase 5 — Weight-resident associative memory

**Goal:** Give the neural model persistent memory without transcript replay or an external semantic database.

**Work**
- Implement `W_FAST` for short-lived associations and `W_MEMORY` for persistent facts/relations.
- Store memory as structured key/value/role tensors that participate in neural retrieval, not as a separate JSON fact database.
- Use a neural encoder to construct keys and values; use query-key similarity or a learned/programmed associative read operation.
- Add provenance, source, confidence, creation time, supersession, and contradiction metadata as tensor fields.
- Implement add, update, supersede, forget, and query operations.
- Use atomic model checkpoints. The checkpoint is the persistent storage format; any crash journal must be temporary and must not become a second semantic memory source of truth.
- Separate episodic records (what happened) from semantic concepts (what relations are believed to hold).

**Deliverables**
- `crates/zerolm-memory/src/fast_weights.rs`
- `crates/zerolm-memory/src/persistent_memory.rs`
- `crates/zerolm-memory/src/retrieval.rs`
- `docs/MEMORY_FORMAT.md`

**GitHub Actions tests**
- Add at least 1,000 synthetic facts through the live update API, then restart from the checkpoint and retrieve them.
- Exact key recall and paraphrase retrieval are scored separately.
- Test collisions, capacity, interference, contradictory facts, supersession, deletion, and memory compaction.
- Prove that semantic facts are present in checkpoint tensor groups and not in `life.json`, transcript files, SQLite, or a vector database.
- Verify that unrelated `W_CORE` tensors remain byte-identical during a memory-only write.
- Corrupt-checkpoint and interrupted-write tests must fail safely or recover the last valid checkpoint.

**Exit gate**
- Persistent recall works across process restarts using only model checkpoint tensors and the model's retrieval computation.
- Memory capacity, retrieval precision/recall, latency, and interference curves are published.

### Phase 6 — Concepts, relations, and compositional reasoning

**Goal:** Move beyond token prediction and exact fact recall to reusable internal concepts and inference.

**Work**
- Build vector representations for entities, types, attributes, actions, relations, events, time, and quantities.
- Implement role-filler binding and unbinding, inspired by the strongest inspectable part of ZeroLM Next.
- Connect language-derived structures to memory without storing complete sentence templates.
- Add controlled inference operators: transitivity, class inclusion, attribute inheritance, comparison, simple arithmetic, temporal ordering, negation, and conditionals.
- Mark inference outputs as derived; preserve the premise provenance and confidence.
- Keep symbolic reference implementations as test oracles, not as hidden runtime substitutes for the neural engine.

**Deliverables**
- `crates/zerolm-engine/src/semantic_state.rs`
- `crates/zerolm-engine/src/binding.rs`
- `crates/zerolm-reasoner/`
- `research/benchmark/compositional_reasoning.py`

**GitHub Actions tests**
- Teach a set of primitive relations, then test unseen combinations and paraphrases.
- Test counterfactual pairs: changing one premise must change the inference when logically required.
- Test contradiction detection and abstention when premises are insufficient.
- Compare against a symbolic reference parser/reasoner and a lookup baseline.
- Run causal ablations of binding, recurrent state, retrieval, and each reasoning operator.
- Use hidden test generation with a seed and publish the seed/hash, not the private test labels.

**Exit gate**
- The model answers new compositional questions from stored primitives and relations, not from a full-sentence lookup.
- Causal ablations demonstrate that the relevant neural pathways are actually used.

### Phase 7 — Grounded learning and interaction

**Goal:** Give concepts meaning through observed consequences, not language strings alone.

**Work**
- Create a deterministic text-and-world simulator with objects, properties, actions, state changes, and causal outcomes.
- Let ZeroLM observe descriptions, make predictions, choose actions, and receive environment results.
- Teach by contrastive examples: similar inputs with different outcomes, interventions, and corrections.
- Add optional visual and audio encoders only after the text-and-world loop passes; do not import pretrained encoders.
- If using CHILDES or another child-directed corpus, feed it as a chronological exposure stream and record it as online learning input. Keep evaluation sets disjoint.

**Deliverables**
- `crates/zerolm-world/`
- `research/environments/`
- `research/benchmark/grounding.py`
- `docs/GROUNDED_LEARNING.md`

**GitHub Actions tests**
- Prediction-before-observation tests: the model must commit to an outcome before seeing the result.
- Intervention tests: change one variable and verify counterfactual predictions change appropriately.
- Action-result learning: performance must improve over a frozen model on unseen combinations.
- Test transfer to new object names, properties, and action sequences.
- Verify the environment result, not the model's own text, is the learning target.

**Exit gate**
- Demonstrable forward transfer from learned experiences to new tasks in a controlled world.
- No claim of physical-world understanding until multimodal grounding has been independently tested.

### Phase 8 — Natural-language generation and multi-turn dialogue

**Goal:** Produce new language from the model's learned internal state.

**Work**
- Implement a recurrent autoregressive decoder over byte or dynamically formed subword tokens.
- Condition generation on recurrent state, retrieved memory, and structured reasoning results.
- Implement interruption, correction, turn boundaries, uncertainty, and explicit “I do not know” behavior.
- Keep current-turn working state separate from persistent memory weights.
- Do not use canned answer paths as the primary generator. Fixed responses may remain only for low-level errors and protocol commands.

**Deliverables**
- `crates/zerolm-engine/src/decoder.rs`
- `crates/zerolm-runtime/src/dialogue.rs`
- `research/benchmark/dialogue.py`

**GitHub Actions tests**
- Generate continuations not present in the exposure stream and not encoded as templates.
- Evaluate response consistency with retrieved facts and reasoning traces.
- Multi-turn tests must survive process restart when the relevant information has been stored in `W_MEMORY`.
- Test hallucination, unsupported questions, calibration, repetition loops, and prompt paraphrases.
- Measure free-generation diversity and degeneration; do not score only exact strings.

**Exit gate**
- The system is a genuine autoregressive neural language model with learned predictive behavior and non-template generation.
- It remains honest about uncertainty and does not present unverified self-generated text as fact.

### Phase 9 — Controlled self-modification and internal WSP

**Goal:** Enable the model to improve the structure of its own neural engine safely.

**Work**
- Formalize a typed WSP patch DSL. Supported operations should include bounded tensor edits, low-rank circuit addition, embedding extension, memory-layout migration, and module activation/deactivation.
- Every patch must include: hypothesis, target tensor/module, preconditions, expected behavior, mathematical effect, resource impact, target tests, protected regression tests, and rollback metadata.
- Implement a deterministic validator and sandboxed candidate model. The active model is never edited in place.
- Initially let developers author WSP patches. Next, let ZeroLM produce patch proposals from its own traces and observed failures. The proposal is not automatically trusted.
- Add a meta-model of its own architecture: tensor names, shapes, dependencies, update policies, invariants, and causal tests.
- Require acceptance to improve a predefined target while preserving old competencies and staying within resource limits.
- Keep an external developer-time programmer as an experimental tool only. The deployed system must not depend on a pretrained external LLM to understand or edit its own weights.

**Deliverables**
- `crates/zerolm-wsp/src/patch.rs`
- `crates/zerolm-wsp/src/validator.rs`
- `crates/zerolm-wsp/src/sandbox.rs`
- `crates/zerolm-wsp/src/rollback.rs`
- `docs/WSP_PROTOCOL.md`

**GitHub Actions tests**
- Schema, tensor shape, value range, and protected-region validation.
- Candidate patch is applied to a copy; active checkpoint hash remains unchanged until acceptance.
- Target tests, all frozen regression suites, adversarial tests, and CPU/RAM budgets run before acceptance.
- Fault injection: malformed patch, NaN, out-of-range edit, failed test, interrupted checkpoint, and rollback.
- Compare the patch against a no-op patch, random patch, and manually authored reference patch.
- Report target gain, regression delta, changed-parameter count, tensor names, and full before/after hashes.
- No patch may edit the tests, evaluator, workflow, or protected manifest.

**Exit gate**
- The engine can propose at least one useful patch from a trace and evidence; the patch passes a hidden evaluation and does not regress protected tasks.
- If it can only apply prewritten patch templates, describe it honestly as rule-based self-maintenance, not autonomous WSP.

### Phase 10 — Developmental capability evaluation

**Goal:** Measure whether the system is becoming more capable over a sequence of experiences.

**Work**
- Build a task ladder across vocabulary, syntax, compositional semantics, memory, arithmetic, causal reasoning, spatial relations, pragmatic inference, dialogue, and grounded interaction.
- Evaluate the same model checkpoint at fixed exposure milestones (for example, after 0, 1k, 10k, 100k, and 1M interaction events; actual milestones depend on Phase 4 throughput).
- Keep hidden test families that are never used as learning data.
- Compare the continual model with frozen-initialized, memory-only, fast-weight-only, WSP-only, and optional online-gradient controls.
- Include tests written by independent contributors and human review of open-ended outputs.
- Use age-normed benchmarks only when their licensing and administration rules permit; never infer an age-equivalent from one benchmark score.

**Deliverables**
- `research/benchmark/developmental_suite/`
- `reports/developmental/learning_curves.json`
- `reports/developmental/forgetting.json`
- `docs/DEVELOPMENTAL_EVALUATION.md`

**GitHub Actions tests**
- Report per-stage performance and learning curves.
- Report average accuracy, forgetting, backward transfer, forward transfer, calibration, memory capacity, and compute cost.
- Require performance improvement on new tasks while bounding regressions on protected old tasks.
- Run multiple seeds and distinguish independent test data from exposure streams.
- Detect benchmark contamination by content hashes and source manifests.

**Exit gate**
- Publish a capability profile with both successes and failures. “Equivalent to a seven-year-old” is not an allowed release claim unless a suitable independent, normed evaluation actually supports that exact statement.

### Phase 11 — CPU deployment, checkpoint durability, and 1.0 release

**Goal:** Turn the validated research engine into a usable local model.

**Work**
- Optimize the measured hot paths using SIMD, cache-aware tensor layouts, and optionally a small BLAS backend. Keep a portable pure-Rust CPU implementation.
- Add CLI, streaming input, local HTTP API, model inspection, memory inspection, and safe backup/restore.
- Support per-user model checkpoints without making external databases the memory source of truth.
- Add model format versioning, migration, checksums, crash-safe atomic saves, and downgrade/rollback support.
- Publish a reproducibility bundle for every release: source commit, compiler, architecture, seed, initial-weight hash, final-weight hash, exposure manifest, benchmark report, and CI run.

**GitHub Actions tests**
- Linux and macOS CPU builds; x86_64 first, ARM64 when runner availability permits.
- Offline execution test: no network access during inference or learning.
- Restart and checkpoint migration tests.
- Resource benchmark on a named, documented runner profile; report p50/p95 latency, tokens/sec, peak RSS, checkpoint size, and update cost.
- CLI/API end-to-end tests and Docker smoke test.
- Full regression and developmental suite.

**Exit gate**
- Reproducible CPU-only release, persistent weight-resident memory, online learning, safe WSP updates, and documented capability boundaries.

## 7. Global benchmark protocol

Every learning experiment must use chronological streams and distinct data roles:

1. **Exposure stream:** examples the model is allowed to observe online, one event at a time.
2. **Development stream:** visible to developers for debugging and iteration; never treated as hidden evidence.
3. **Frozen regression set:** used to detect forgetting and collateral damage; labels are not exposed to the update controller.
4. **Hidden evaluation set:** held out until a phase gate or release evaluation. No patch generator or model component may read its labels.
5. **Adversarial set:** malformed, contradictory, ambiguous, and out-of-distribution inputs.

Report at least:

- next-token bits-per-byte/perplexity before and after exposure;
- held-out token prediction and compositional generalization;
- task accuracy at each exposure milestone;
- average accuracy and average forgetting;
- backward and forward transfer;
- exact memory recall and paraphrase retrieval;
- calibration and abstention quality;
- number and magnitude of parameter updates;
- percentage of parameters changed by each update class;
- inference and update latency, RAM, and checkpoint size;
- performance over at least three seeds for research claims.

A fixed set of generated grammar examples is useful for unit tests but cannot be the only evidence. Include independent human-written prompts, external benchmark tasks, adversarial inputs, and environment-based evaluations.

## 8. Critical risks and kill criteria

| Risk | Why it matters | Required response / kill criterion |
|---|---|---|
| Bootstrap language is too weak | The model cannot understand enough to learn from natural interaction | First prove the teaching protocol and byte-level predictor; do not pretend the model begins with English competence |
| Non-gradient plasticity cannot learn syntax | Fast weights may memorize associations without learning general language structure | Compare with frozen and online-gradient controls; if the strict rule fails, report it and decide whether online gradients are permitted |
| Self-generated feedback loop | The model may reinforce its own errors | Only learn from observed next tokens, verified outcomes, or external correction; never treat a sampled answer as truth automatically |
| Catastrophic forgetting | New experience damages prior capabilities | Maintain protected tests, fast/slow parameter separation, consolidation, and rollback |
| Memory interference | Weight-based associations collide as memory grows | Measure recall-vs-capacity and interference; add sparse/low-rank allocation only when evidence justifies it |
| WSP is mistaken for an optimizer | Editing weights does not guarantee useful new capabilities | Keep patch hypotheses, causal traces, independent tests, and negative results; WSP is not a substitute for an acquisition algorithm |
| External LLM dependency | An external pretrained model doing the reasoning would invalidate the self-developing claim | External model may assist development only; runtime self-modification must eventually work without it |
| CPU limits | Larger recurrent state and associative memory can still be expensive | Profile every phase on named CPU targets and cap dimensions by measured budgets |
| “Age equivalence” overclaim | Child development is multidimensional and grounded | Publish capability-specific results; no age-equivalent claim without independent normed evaluation |

**Stop/go rule:** if Phase 4 cannot show measurable held-out acquisition from chronological input, do not proceed to claims about a self-developing language model. Continue only as a research project on learning rules and small task-specific networks until the core acquisition hypothesis is supported.

## 10. Recommended implementation order

The engineering order should be:

1. Phase 0 and Phase 1: definitions and reproducible baseline.
2. Phase 2: neural runtime and architecture bake-off.
3. Phase 3: byte bootstrap and deterministic initialization.
4. Phase 4: first online language prediction and acquisition gate.
5. Phase 5: persistent weight-resident memory.
6. Phase 6: compositional concepts and reasoning.
7. Phase 7: grounded interaction.
8. Phase 8: open-ended neural generation and dialogue.
9. Phase 9: model-proposed WSP patches and controlled structural evolution.
10. Phase 10: developmental capability evaluation.
11. Phase 11: CPU deployment and release.

Do not implement the full architecture in one large branch. Each phase should land as a small PR with its own tests, report schema, CI summary, and updated research log.

## Final research position

The realistic near-term research claim is not “we will create a twenty-year-old human-like mind.” It is:

> **We will test whether a small neural language system, initialized only by explicit programmatic design and without offline pretraining, can acquire progressively more language-modeling, memory, and reasoning capability from a chronological stream of observations using online plasticity and controlled weight-space evolution.**

This is a difficult but falsifiable research objective. The first decisive milestone is Phase 4: show that the same initially untrained neural engine learns from a stream and improves on unseen examples. Everything beyond that depends on passing this gate.
